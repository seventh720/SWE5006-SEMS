# 取消联动与事务一致性

更新：2026-10-20。当前免费票出票、核销、通知与统计已集成；支付/退款不在本期范围。

## 已实现

- 个人取消、活动取消沿用已有 HTTP 接口和权限，新增同步 `BookingCancelled` 事件。
- 订单、票券作废和库存释放在同一数据库事务中完成；任何监听器异常使整个操作回滚。
- 新增 `issued_tickets` 及票券状态基础。取消无票券的旧订单仍正常工作；已有确认订单可通过内部出票接口补票。
- 出票、核销、个人取消、活动取消均先锁活动行，再读取订单和票券，锁一直持有到提交。
- 个人订单包含已核销票时，整笔取消返回 `409`，订单、库存和所有票券不变。活动开始后的个人取消限制继续保留。
- 组织者取消活动会作废全部有效订单的票券，包括已核销票；`checked_in_at` 保留历史，`voided_at` 记录作废时间。库存继续按取消订单数量返还一次。

## 票券状态

| 操作 | 变化 | 约束 |
|---|---|---|
| 出票 | 新建 `VALID` | 活动为 PUBLISHED、订单为 CONFIRMED；每单每个序号唯一；重复调用返回原票 |
| 核销 | `VALID → CHECKED_IN` | 活动及订单仍有效；票券属于指定订单和活动；再次核销返回409 |
| 个人取消 | `VALID → VOID` | 整单没有已核销票，且活动尚未开始 |
| 活动取消 | `VALID / CHECKED_IN → VOID` | 保留核销历史；不可再次出票或核销 |

取消后的旧下单幂等请求仍返回原取消订单，不重新扣库存，不触发出票。活动取消接口的版本校验保持原有行为，重复取消活动仍可能返回409。

## 给其他模块的接口

以下均为 Java 内部应用接口，**没有对外 HTTP 路由**。不能跳过归属校验或 STAFF 活动授权后直接暴露给前端。

| 接口 | 调用方 | 接入要求 |
|---|---|---|
| `TicketLifecycleService.issue(eventId, bookingId)` | 黄浩扬的电子票模块 | 校验本人订单或由已确认订单流程可信调用；返回逐张 `TicketView`，可补发旧订单；不可给取消订单补票 |
| `TicketLifecycleService.checkIn(eventId, bookingId, ticketId)` | 罗润洲的签到模块 | 校验STAFF角色、具体活动授权及签到时间规则；同一事务内保存操作者和签到记录，失败时一起回滚 |
| `BookingAccessService.lockActive(eventId, bookingId)` | 票券等内部业务 | 必须已有事务；锁活动后读取有效订单，返回订单ID、活动ID及数量，不暴露个人资料 |
| `BookingCancelled(bookingId, eventId, reason)` | 票券及后续通知模块 | 同步监听，使用调用方事务；reason为ATTENDEE_CANCELLED或EVENT_CANCELLED |

接入方不要在锁活动之前加载可变订单/票券实体，否则JPA一级缓存可能保留旧状态。跨模块只能使用公开服务或事件，不直接引用其他模块Entity/Repository。活动取消会依次发布每个订单的取消事件；监听器不要另开事务、异步处理，或捕获失败后继续提交。

工作人员授权/撤权与核销按同一锁顺序协调：先在同一事务锁活动，再检查授权、调用核销及写签到记录；撤权也锁该活动，以保证撤权提交后不能再通过旧授权核销。

## 出票与核销接入

确认订单已同步发布带 bookingId/eventId 的 BookingConfirmed，由票务监听器在同一事务出票。POST /api/v1/bookings/{bookingId}/tickets 校验 ATTENDEE 及订单归属，按活动锁顺序读取状态：有效旧订单幂等补票，取消订单只返回现有 VOID 票，不重新出票。订单详情提供电子票 QR 页面。

Staff 核销执行活动授权、签到窗口检查并保存操作审计；组织者界面提供分配及撤销，通知与报表已接入。结果见[云端验收](acceptance/sprint4-2026-10-20/README.md)和[测试记录](testing.zh-CN.md)。
