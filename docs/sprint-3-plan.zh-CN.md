## 3. Sprint Goal 与范围

**Sprint Goal：组织者能为自己的活动配置票种和库存；参与者能对尚未开始的已发布活动完成免费预订、查看和取消自己的订单；并发、重复提交和活动取消均保持订单与库存一致。**

### 必须交付

1. 票种名称、价格、币种、配额及剩余库存；所有票种总配额不超过活动容量。
2. 组织者本人活动的票种配置与订单列表。
3. 免费票预订：服务端校验、原子扣减、重复请求保护。
4. 我的订单列表、详情、取消及库存返还。
5. 活动取消同步取消有效订单；历史订单保留活动与票种快照。
6. PostgreSQL 迁移与并发测试、前端交互、真实浏览器演示、Sprint 1/2 回归。
7. Sprint 4 的订单/票券/支付状态及工作人员授权接口约定，形成简短设计文档。

### 本轮范围限制

- 一笔订单只含一个票种，可购买多张；建议每单 1–10 张。暂不增加购物车和多票种结算。
- 支持记录非负价格，统一 SGD、最小货币单位整数；本轮仅允许零价票下单。付费票显示价格和“暂未开放购买”，后端同样拒绝付费预订，不能伪记为已支付。
- 免费订单直接确认，不引入待支付库存占用或超时释放任务；这些随 Sprint 4 支付方案一并实现。
- 本轮订单确认不等于已发行二维码票券；页面显示预订编号，Sprint 4 再出票。

## 7. 业务与技术约定（D1 冻结）

### 7.1 票种、容量与历史兼容

- `ticket_types` 建议包含活动 ID、名称、`price_minor`、`currency`、配额、已预订数、版本及审计时间。数据库约束确保价格非负、`0 ≤ booked_quantity ≤ quota`。
- 总票种配额不得超过 `events.capacity`；剩余库存为配额减去有效预订数量。检查总配额与写入必须在同一事务中串行化。
- 本轮票种可在本人草稿或未来开始的已发布活动下配置；取消或已开始活动不可配置。首次预订后冻结票种名称、价格和配额，避免引入改价/缩容规则；不提供物理删除。
- 草稿修改活动容量时，同样校验不低于已配置票种总配额。票种配置与活动编辑应遵循同一并发约束。
- 保留 Sprint 2 无票种也能发布的行为；无票种活动显示“暂未开放预订”。不自动给旧活动创建可售库存或订单。

### 7.2 订单、幂等与取消

- `bookings` 建议包含用户/活动/票种 ID、数量、单价及总额快照、币种、活动标题/地点/时间和票种名称快照、订单状态、取消原因、请求键与审计时间。金额由服务端计算并检查溢出。
- 本轮状态为 `CONFIRMED → CANCELLED`；取消原因区分参与者主动取消和活动取消。免费订单的支付状态明确为 `NOT_REQUIRED`。
- `Idempotency-Key` 由客户端为一次下单生成，重试复用；数据库对 `(user_id, request_key)` 建唯一约束，并保存可核对的请求参数。同键同参数返回既有订单，同键异参数 `409`；新一次预订需新键。
- 已确认订单的库存扣减、订单写入必须同事务成功或回滚；取消采用条件状态转换，使库存最多返还一次。
- 用户在活动开始前可取消本人有效订单。组织者取消活动时，全部有效订单改为取消、记录原因并返还计数；活动不可恢复，返还不重新开放售票。
- 取消活动的公开详情仍按 Sprint 2 返回 `404`。我的订单通过订单快照显示历史及取消状态，不能依赖公开活动详情维持可读性。

### 7.3 并发与模块边界

- 延续模块化单体；模块只通过公开应用接口协作，不能直接引用另一模块内部 Entity/Repository。
- 建议采用 PostgreSQL 事务和一致的锁顺序：先活动，再票种（多条按 ID 排序），再订单。活动取消、下单、取消订单和票种/容量修改均遵循此约定。
- 活动模块提供可参与调用方事务的状态/归属校验及加锁入口；票务模块提供配额占用和返还入口；订单模块负责订单与幂等。通过明确的应用协调入口保证单库事务覆盖整个操作。
- 现有活动乐观锁不能单独保证新订单与活动取消一致。必须有并发集成测试证明取消与下单在同一活动上正确串行化；失败时不能残留有效订单或错误库存。
- Sprint 4 扩展待支付、失败/超时、支付成功、退款及票券失效时，沿用以上一致性约束；D10 输出转换表与迁移方案，不预先建空壳接口。

### 7.4 权限和建议 API

| 操作 | 权限 |
|---|---|
| 读取公开票种 | 匿名可读，仅已发布活动；草稿/取消活动 `404` |
| 配置票种、读取活动订单 | ORGANIZER 或 ADMIN，且活动归属本人；ADMIN 不跨组织者代管 |
| 创建、查看、取消我的订单 | ATTENDEE，用户 ID 从 JWT 获取；只处理本人订单 |
| STAFF 单独角色 | 本轮无票种或预订写权限；兼有其他角色时按相应角色授权 |

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/v1/events/{eventId}/ticket-types` | 公开票种及剩余库存 |
| GET / POST | `/api/v1/organizer/events/{eventId}/ticket-types` | 本人票种列表 / 创建 |
| PUT | `/api/v1/organizer/events/{eventId}/ticket-types/{ticketTypeId}` | 携带版本修改未售出票种 |
| POST | `/api/v1/bookings` | 携带请求键创建订单，首次成功 `201`，重放 `200` |
| GET | `/api/v1/bookings` | 本人订单分页 |
| GET | `/api/v1/bookings/{id}` | 本人订单详情 |
| POST | `/api/v1/bookings/{id}/cancel` | 本人取消，重复取消返回已有结果 |
| GET | `/api/v1/organizer/events/{eventId}/bookings` | 本人活动订单分页 |

复用现有活动取消接口并扩展其事务行为。延续现有分页结构、默认 10/上限 50、含时区 ISO 8601 时间及 Problem JSON。未登录 `401`、角色不符 `403`、对象不存在或非本人 `404`、输入非法 `400`、售罄/不可预订/版本或幂等冲突 `409`。票种必须属于请求中的活动，不能只校验票种 ID 存在。API 字段和错误码在 D1 契约中给出实例。

## 8. 测试重点与完成定义

### 必测场景

1. 新建及旧有活动配置票种，超总容量、负价、零配额、草稿缩容冲突被拒绝。
2. 最后 1 张票并发争抢、跨票种总容量约束、下单中途失败回滚；最终订单数量与库存一致。
3. 同键串行及并发重试只产生一笔订单；异参数冲突；取消后的旧请求重试不再扣库存。
4. 重复取消、并发取消只返还一次；取消活动与下单/用户取消并发，结果无有效残留订单。
5. 草稿、取消、已开始活动及付费票不能完成本轮免费预订；不能伪造用户、金额、活动归属或票种所属。
6. 参与者之间、组织者之间的数据隔离，STAFF 单独角色拒绝，管理员仍遵守本人活动边界。
7. 活动取消后订单历史可读；服务器重启后订单和库存一致。
8. 前端登录返回、数量校验、重复点击、售罄、网络重试、401/403/404/409、空列表及移动视口反馈。
9. 空库建表和 Sprint 2 数据升级成功，用户、角色及活动保留；认证、角色分配、活动搜索/发布/取消回归通过。

### Definition of Done

- US-301–309 逐条记录通过/失败、证据及遗留问题，真实 PostgreSQL 和前后端闭环通过。
- 后端运行 `mvn verify` 及 `RUN_CONTAINER_TESTS=true mvn test`；前端运行 `npm ci`、`npm run typecheck`、`npm test`、`npm run build`，保存实际结果。
- `backend`、`backend-integration`、`frontend` 三项最终提交 CI 通过，至少一名其他组员批准 PR，审查问题解决并按团队流程合并。
- 新增 Flyway 迁移、代码、测试、ERD、数据字典一起交付；不修改已执行迁移。
- Docker 全栈构建、浏览器端到端、重启持久化及移动视口通过；验收报告和截图有可访问的仓库位置。
- 更新 README 当前进度、入口和演示步骤；没有阻断流程、越权、超卖或库存损坏的未解决缺陷。
- Sprint 4 需求清单、支付边界、票券状态、工作人员活动授权及主要任务估算明确。

## 9. Sprint Review 演示脚本

1. 准备组织者 A/B、参与者 A/B；沿用管理员分配角色后重新登录的流程。
2. 组织者 A 创建容量 3 的未来活动，设置两个免费票种，配额分别 2 和 1；展示超容量配置被拒绝，随后发布。
3. 参与者 A 预订 1 张，在我的订单中确认数量与状态；重放请求，确认只有一笔订单。
4. 对剩余最后 1 张同票种门票发出并发预订，展示只有一个成功及一致的库存。
5. A 取消本人订单并重复取消，展示库存只恢复一次；B 读取 A 的订单被拒绝。
6. 保留至少一笔有效订单，由组织者 A 取消活动；展示公开隐藏、历史订单显示活动取消且无有效预订残留。
7. 展示组织者 B 无法管理 A 的票种和订单，以及自动化并发/回滚测试、升级、重启及 CI 证据。
8. 展示 Sprint 4 已排好的出票、签到、通知、报表及支付任务，确认 Sprint 5 留给验收与交付。
